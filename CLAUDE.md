## Supabase

Project `recruitLens` (`sytbbdmrkzfrpqtmioiv`), same org as the sibling `interview-os` project. Tables:
- `profiles` — the app's user table, one row per `auth.users` row (`id uuid primary key references auth.users(id)`, plus `email`), kept in sync by a `handle_new_user()` trigger on `auth.users` insert. A place to hang future per-user preferences (e.g. an email-alert opt-in) — nothing reads/writes it directly yet beyond the trigger. `handle_new_user()` is `SECURITY DEFINER` and has `EXECUTE` revoked from `anon`/`authenticated`/`public` (see `supabase/migrations/20260828220100_restrict_handle_new_user_execute.sql`) since it's only meant to run via the trigger, not be called directly.
- `leetcode_account` — one row per user (`user_id uuid primary key references auth.users(id)`). Holds `username`, `sync_status` (`'idle' | 'syncing' | 'error'`), `last_synced_at`, `last_error`, and the solved-count stats (`solved_count`/`easy_count`/`medium_count`/`hard_count`).
- `user_companies` — per-user company flags for the Company Questions tab, one row per `(user_id, company_name)` (PK; `user_id` defaults to `auth.uid()`, `company_name` free text matching `lc_companies.name`). Holds `is_pinned`/`pinned_at` (pinned companies lead the quick-pick grid, ordered by `pinned_at`) and `is_in_process` (the header's "In process" toggle — setting it also pins the company, and Pin is disabled while it's on). RLS: authenticated, own rows only. Read/written via `src/lib/userCompanies.ts` → `useUserCompanies` (optimistic, background upserts that only write the flags being changed). Replaced the short-lived `pinned_companies` table.
- `leetcode_problems` (shared/global — LeetCode problem metadata, not user-owned, `slug` unique) / `leetcode_solves` (child, `problem_id` FK `on delete cascade`, `user_id` FK, `unique (user_id, problem_id)` — one solve per problem *per user*, not globally) — populated by the `leetcode-sync` Edge Function from LeetCode's public GraphQL API. That API hard-caps `recentAcSubmissionList` at 20 entries regardless of the requested limit, so a sync only ever sees the most recent 20 accepted submissions — `leetcode_solves` accumulates across repeated syncs, it isn't backfilled in one shot. Besides the manual Sync / Resync control next to the Company Questions heading (`src/components/companies/LeetCodeSync.tsx`), `useLeetCodeSync` fires a silent change probe (`{ mode: "check" }`) on app load and tab refocus, throttled to once per 5 min via `leetcode_account.last_checked_at`: the function fetches only the newest accepted submission and runs the full sync only if its id differs from `latest_submission_id`. `last_changed_at` bumps only when a sync saw new submissions — `useLeetCodeSolvedSlugs` refetches on it. `pg_cron` background resync is still deferred (see `leetcodeSyncTodo.md`).
- `lc_companies` / `lc_questions` / `lc_topics` / `lc_question_topics` / `lc_company_questions` — normalized `[company] -> [time window] -> [question]` schema, sourced from `github.com/liquidslr/leetcode-company-wise-problems` (~470 companies) and imported via `scripts/import-company-questions.ts` (`npm run import:company-questions`, one-off/rerunnable, needs a `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` — never `VITE_`-prefixed, must not reach the client bundle). `lc_questions` is deduped by LeetCode slug; `lc_company_questions` is the fact table (`company_id`, `question_id`, `time_window` one of `'30days' | '3months' | '6months' | '6months_plus' | 'all_time'`, `frequency_score`, `acceptance_rate`), one row per `(company, question, time_window)`. `lc_topics`/`lc_question_topics` hold each question's LeetCode topic tags (e.g. "Array", "Hash Table") as a real many-to-many relation, not a flattened string. Not managed by this app at runtime — imported separately, read-only from the frontend via `src/lib/companyQuestions.ts` (matches `lc_companies.name` by exact, case-insensitive name). Rendered by the `Company Questions` tab (`src/components/companies/CompaniesBoard.tsx`): a quick-pick grid (`FeaturedCompanies.tsx` — a selected company that's neither pinned nor featured takes the first slot, then the user's pins, then a hardcoded featured list filling the rest) plus full-bank search (`CompanyPicker.tsx`). Tiles show live stats from the `company_stats(names text[])` SQL function (distinct questions, how many were asked in the last 30 days, easy/medium/hard mix, and the caller's solved count via `leetcode_solves`), and before a company is picked the board shows `TrendingQuestions.tsx` from `trending_questions(max_rows)` (questions asked by the most companies in the last 30 days). Both are `SECURITY INVOKER` (so RLS keeps `solved` per-user) — see `supabase/migrations/20261030120000_company_stats_functions.sql`, called via `src/lib/companyStats.ts`. **Company hues:** every company gets one of eight `--hue-*` tokens (`tokens.css`, light and dark values) via `src/lib/companyColors.ts` (hand-picked for the featured list, hashed otherwise), shown as a two-letter `CompanyMonogram`; picking a company sets `--company-hue` on `.companies-board`, and the progress arc, radar, topic bars, frequency bars, pin buttons and active filters all derive from it (falling back to `--accent` elsewhere). Schema DDL lives in `supabase/migrations/` (also applied directly via the Supabase MCP `apply_migration` tool — no local Supabase CLI project in this repo).
- `job_postings` — new-grad postings synced every 30 minutes from three GitHub-hosted lists (`jobright-ai/2026-Software-Engineer-New-Grad`'s README table, `speedyapply/2027-SWE-College-Jobs`'s `NEW_GRAD_USA.md` tables, `SimplifyJobs/New-Grad-Positions`'s structured `.github/scripts/listings.json`) via `scripts/import-job-postings.ts` (`npm run import:job-postings`, same service-role-key convention as the LeetCode import). Dedup key is `url_key`, a generated column normalizing the apply `url` (lowercased, query/fragment stripped) — the same posting appearing in 2+ source lists collapses into one row, with `sources` (a `text[]`) recording which lists cited it, rather than "filtering out" the duplicate by dropping it. Rows are soft-deleted (`is_active = false`) when a sync no longer sees them in any source, never hard-deleted, matching the `leetcode_*`/`lc_*` convention. Scheduled every 30 minutes via `.github/workflows/sync-jobs.yml` (this repo's only GitHub Actions workflow — needs `VITE_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set as repo secrets); also runnable manually. Read in the frontend via `src/lib/jobPostings.ts` → `useJobPostings` → the `Jobs` tab's `JobsBoard` component — browse/filter only.

**Auth is real per-user multi-tenancy** (`supabase/migrations/20260828220000_add_user_scoping.sql`). `AuthContext` (`src/context/AuthContext.tsx`, consumed via `useAuth()`) wraps Supabase Auth: Google OAuth plus email/password sign-in, sign-up (email + password only, nothing else collected) and password reset. `App.tsx` renders the marketing `LandingPage` (`src/components/landing/LandingPage.tsx`, styles in `src/styles/landing.css`) until a session exists — its Sign in / Sign up / "Start your free week" buttons open `AuthDialog` (a native `<dialog>` around `src/components/auth/AuthForm.tsx`), and its live counts come from `src/lib/landingStats.ts` (anon-readable `head: true` count queries). "Confirm email" is on in the project, so sign-up shows "check your email" until the user clicks the link. A password-reset link signs the user in with a recovery session; `AuthContext.passwordRecovery` makes `App.tsx` show `SetPasswordScreen` until they save a new password. Supabase's built-in mailer is heavily rate-limited and only meant for testing — production email needs custom SMTP (Authentication → Emails → SMTP settings in the dashboard). The "$7/month, first week free, 20% to Rooted Immigrant Collective" pricing it shows is backed by Stripe (see **Billing** below); the display price, trial length and charity live in constants at the top of `src/lib/billing.ts`. `App.tsx` and reads `session?.user.id` to pass a `userId` into `useLeetCodeSync`. Requires the Google provider to be enabled in the Supabase dashboard (Authentication → Providers → Google, with a Google Cloud OAuth client whose authorized redirect URI is `https://sytbbdmrkzfrpqtmioiv.supabase.co/auth/v1/callback`) — that's a manual dashboard step, not something in this repo. RLS on `leetcode_account`/`leetcode_solves`/`user_companies` is `authenticated`-only, scoped to `auth.uid() = user_id`. `leetcode_problems`, the `lc_*` question-bank tables, and `job_postings` are intentionally shared/global reference data — not user-owned, left unscoped.

**Edge Function:** `leetcode-sync` (deployed via Supabase, not part of this repo's build — see the project's Edge Functions in the Supabase dashboard) calls LeetCode's public GraphQL endpoint server-side (the browser can't call it directly — LeetCode's CORS headers only allow `leetcode.com` as an origin) and writes to `leetcode_account`/`leetcode_problems`/`leetcode_solves` using the service role key. Invoked from the frontend via `supabase.functions.invoke("leetcode-sync", { body })` in `src/lib/leetcode.ts` — an empty body resyncs the already-connected username, `{ username }` connects a new one. `supabase.functions.invoke` forwards the caller's session JWT automatically; the function decodes it (`supabase.auth.getUser(token)`) to get the caller's `user_id` rather than trusting a client-supplied value, since `verify_jwt: true` already guarantees the gateway rejected unauthenticated calls before the function body runs.

**Billing (Stripe):** $7/month (20% of revenue goes to Rooted Immigrant Collective — copy only, no Stripe Connect/automatic transfer), 7-day free trial with card collected upfront by Stripe Checkout (trial only on a user's first subscription — `subscriptions.has_used_trial`). Gated by `VITE_BILLING_ENABLED`; when on, signed-in users without a `trialing`/`active`/`past_due` subscription see `src/components/billing/Paywall.tsx` instead of the app, and the account menu (`src/components/layout/AccountMenu.tsx`, the avatar in the top-right corner) gets a "Manage billing" item linking to the Stripe Billing Portal, with a status line from `subscriptionStatusLine` in `src/lib/billing.ts`.
- `subscriptions` table (`supabase/migrations/20261029180000_create_subscriptions.sql`) — one row per user mirroring their Stripe customer/subscription. RLS: authenticated can `select` own row only; writes come only from the Edge Functions via service role. Read via `src/lib/billing.ts` → `useSubscription` (polls after `?checkout=success` until the webhook lands).
- Edge Functions (source in `supabase/functions/`, shared helpers in `_shared/billing.ts`): `stripe-checkout` (`verify_jwt: true`; `{ action: "checkout" | "portal" }` → returns a Stripe URL) and `stripe-webhook` (**must** be deployed with `--no-verify-jwt`; verifies `Stripe-Signature`, re-fetches the subscription from Stripe and upserts the row). Both need Supabase secrets `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; without them they return a 503 "Billing isn't set up yet".
- `npm run setup:stripe` (`scripts/setup-stripe.ts`, idempotent) creates the product + price (lookup key `vantage_monthly` — checkout falls back to an inline $7 price if it's missing; changing `PRICE_CENTS` and re-running creates a new price, moves the lookup key to it and archives the old one, so existing subscribers keep their old price), the webhook endpoint at `<VITE_SUPABASE_URL>/functions/v1/stripe-webhook`, and a Billing Portal configuration, then prints the `supabase secrets set` command.
- Going live: `STRIPE_SECRET_KEY` in `.env.local` → `npm run setup:stripe` → set the two Supabase secrets → apply the migration → `npx supabase functions deploy stripe-checkout --project-ref sytbbdmrkzfrpqtmioiv` and `npx supabase functions deploy stripe-webhook --no-verify-jwt --project-ref sytbbdmrkzfrpqtmioiv` → `VITE_BILLING_ENABLED=true`. Test-mode keys (`sk_test_…`) first; re-run the whole list with `sk_live_…` for production (live mode has its own price/webhook/secret).
- Type-check the functions with `cd supabase/functions && npx deno check --node-modules-dir=none stripe-checkout/index.ts stripe-webhook/index.ts` (without that flag Deno trips over the repo's `node_modules`).

## Architecture

React 18 + TypeScript + Vite. Styling is hand-written CSS custom properties (`src/styles/tokens.css` + `global.css`, plus `landing.css` for the signed-out landing page) — no Tailwind, no CSS framework. No React Router — the tab bar is local state in `App.tsx`. No global state library.

`App.tsx`'s `Tab` union is `"Company Questions" | "Jobs"`, both functional. If a new tab is added to the union before it has a real view behind it, render it disabled with a "Soon" badge (`tab-bar__tab--disabled` / `tab-bar__soon`), don't build a placeholder page for it.

**State:** `AuthContext` for the login gate, `ThemeContext` (`src/context/ThemeContext.tsx`, light/dark, persisted to `localStorage` under `vantage-theme`; switched from the account menu in the app, and from `ThemeToggle` on the signed-out/paywall screens), and otherwise plain per-feature hooks (`useLeetCodeSync`, `useUserCompanies`, `useLcCompanies`, `useCompanyQuestions`, `useLeetCodeSolvedSlugs`, `useJobPostings`) that fetch from Supabase into `useState`.
