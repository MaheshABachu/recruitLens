## Supabase

Project `recruitLens` (`sytbbdmrkzfrpqtmioiv`), same org as the sibling `interview-os` project. Tables:
- `profiles` — the app's user table, one row per `auth.users` row (`id uuid primary key references auth.users(id)`, plus `email`), kept in sync by a `handle_new_user()` trigger on `auth.users` insert. A place to hang future per-user preferences (e.g. an email-alert opt-in) — nothing reads/writes it directly yet beyond the trigger. `handle_new_user()` is `SECURITY DEFINER` and has `EXECUTE` revoked from `anon`/`authenticated`/`public` (see `supabase/migrations/20260828220100_restrict_handle_new_user_execute.sql`) since it's only meant to run via the trigger, not be called directly.
- `leetcode_account` — one row per user (`user_id uuid primary key references auth.users(id)`). Holds `username`, `sync_status` (`'idle' | 'syncing' | 'error'`), `last_synced_at`, `last_error`, and the solved-count stats (`solved_count`/`easy_count`/`medium_count`/`hard_count`).
- `user_companies` — per-user company flags for the Company Questions tab, one row per `(user_id, company_name)` (PK; `user_id` defaults to `auth.uid()`, `company_name` free text matching `lc_companies.name`). Holds `is_pinned`/`pinned_at` (pinned companies lead the quick-pick grid, ordered by `pinned_at`) and `is_in_process` (the header's "In process" toggle — setting it also pins the company, and Pin is disabled while it's on). RLS: authenticated, own rows only. Read/written via `src/lib/userCompanies.ts` → `useUserCompanies` (optimistic, background upserts that only write the flags being changed). Replaced the short-lived `pinned_companies` table.
- `leetcode_problems` (shared/global — LeetCode problem metadata, not user-owned, `slug` unique) / `leetcode_solves` (child, `problem_id` FK `on delete cascade`, `user_id` FK, `unique (user_id, problem_id)` — one solve per problem *per user*, not globally) — populated by the `leetcode-sync` Edge Function from LeetCode's public GraphQL API. That API hard-caps `recentAcSubmissionList` at 20 entries regardless of the requested limit, so a sync only ever sees the most recent 20 accepted submissions — `leetcode_solves` accumulates across repeated syncs, it isn't backfilled in one shot. Besides manual Connect/Resync from the settings panel, `useLeetCodeSync` fires a silent change probe (`{ mode: "check" }`) on app load and tab refocus, throttled to once per 5 min via `leetcode_account.last_checked_at`: the function fetches only the newest accepted submission and runs the full sync only if its id differs from `latest_submission_id`. `last_changed_at` bumps only when a sync saw new submissions — `useLeetCodeSolvedSlugs` refetches on it. `pg_cron` background resync is still deferred (see `leetcodeSyncTodo.md`).
- `lc_companies` / `lc_questions` / `lc_topics` / `lc_question_topics` / `lc_company_questions` — normalized `[company] -> [time window] -> [question]` schema, sourced from `github.com/liquidslr/leetcode-company-wise-problems` (~470 companies) and imported via `scripts/import-company-questions.ts` (`npm run import:company-questions`, one-off/rerunnable, needs a `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` — never `VITE_`-prefixed, must not reach the client bundle). `lc_questions` is deduped by LeetCode slug; `lc_company_questions` is the fact table (`company_id`, `question_id`, `time_window` one of `'30days' | '3months' | '6months' | '6months_plus' | 'all_time'`, `frequency_score`, `acceptance_rate`), one row per `(company, question, time_window)`. `lc_topics`/`lc_question_topics` hold each question's LeetCode topic tags (e.g. "Array", "Hash Table") as a real many-to-many relation, not a flattened string. Not managed by this app at runtime — imported separately, read-only from the frontend via `src/lib/companyQuestions.ts` (matches `lc_companies.name` by exact, case-insensitive name). Rendered by the `Company Questions` tab (`src/components/companies/CompaniesBoard.tsx`): a quick-pick grid (`FeaturedCompanies.tsx` — a selected company that's neither pinned nor featured takes the first slot, then the user's pins, then a hardcoded featured list filling the rest) plus full-bank search (`CompanyPicker.tsx`). Schema DDL lives in `supabase/migrations/` (also applied directly via the Supabase MCP `apply_migration` tool — no local Supabase CLI project in this repo).
- `job_postings` — new-grad postings synced daily from three GitHub-hosted lists (`jobright-ai/2026-Software-Engineer-New-Grad`'s README table, `speedyapply/2027-SWE-College-Jobs`'s `NEW_GRAD_USA.md` tables, `SimplifyJobs/New-Grad-Positions`'s structured `.github/scripts/listings.json`) via `scripts/import-job-postings.ts` (`npm run import:job-postings`, same service-role-key convention as the LeetCode import). Dedup key is `url_key`, a generated column normalizing the apply `url` (lowercased, query/fragment stripped) — the same posting appearing in 2+ source lists collapses into one row, with `sources` (a `text[]`) recording which lists cited it, rather than "filtering out" the duplicate by dropping it. Rows are soft-deleted (`is_active = false`) when a sync no longer sees them in any source, never hard-deleted, matching the `leetcode_*`/`lc_*` convention. Scheduled daily at noon ET via `.github/workflows/sync-jobs.yml` (this repo's only GitHub Actions workflow — needs `VITE_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set as repo secrets); also runnable manually. Read in the frontend via `src/lib/jobPostings.ts` → `useJobPostings` → the `Jobs` tab's `JobsBoard` component — browse/filter only.

**Auth is real per-user multi-tenancy** (`supabase/migrations/20260828220000_add_user_scoping.sql`). `AuthContext` (`src/context/AuthContext.tsx`, consumed via `useAuth()`) wraps Supabase Auth's Google OAuth (`supabase.auth.signInWithOAuth({ provider: "google" })`) — `App.tsx` renders `LoginScreen` until a session exists, and reads `session?.user.id` to pass a `userId` into `useLeetCodeSync`. Requires the Google provider to be enabled in the Supabase dashboard (Authentication → Providers → Google, with a Google Cloud OAuth client whose authorized redirect URI is `https://sytbbdmrkzfrpqtmioiv.supabase.co/auth/v1/callback`) — that's a manual dashboard step, not something in this repo. RLS on `leetcode_account`/`leetcode_solves`/`user_companies` is `authenticated`-only, scoped to `auth.uid() = user_id`. `leetcode_problems`, the `lc_*` question-bank tables, and `job_postings` are intentionally shared/global reference data — not user-owned, left unscoped.

**Edge Function:** `leetcode-sync` (deployed via Supabase, not part of this repo's build — see the project's Edge Functions in the Supabase dashboard) calls LeetCode's public GraphQL endpoint server-side (the browser can't call it directly — LeetCode's CORS headers only allow `leetcode.com` as an origin) and writes to `leetcode_account`/`leetcode_problems`/`leetcode_solves` using the service role key. Invoked from the frontend via `supabase.functions.invoke("leetcode-sync", { body })` in `src/lib/leetcode.ts` — an empty body resyncs the already-connected username, `{ username }` connects a new one. `supabase.functions.invoke` forwards the caller's session JWT automatically; the function decodes it (`supabase.auth.getUser(token)`) to get the caller's `user_id` rather than trusting a client-supplied value, since `verify_jwt: true` already guarantees the gateway rejected unauthenticated calls before the function body runs.

## Architecture

React 18 + TypeScript + Vite. Styling is hand-written CSS custom properties (`src/styles/tokens.css` + `global.css`) — no Tailwind, no CSS framework. No React Router — the tab bar is local state in `App.tsx`. No global state library.

`App.tsx`'s `Tab` union is `"Company Questions" | "Jobs"`, both functional. If a new tab is added to the union before it has a real view behind it, render it disabled with a "Soon" badge (`tab-bar__tab--disabled` / `tab-bar__soon`), don't build a placeholder page for it.

**State:** `AuthContext` for the login gate, `ThemeContext` (`src/context/ThemeContext.tsx`, light/dark, persisted to `localStorage` under `vantage-theme`), and otherwise plain per-feature hooks (`useLeetCodeSync`, `useUserCompanies`, `useLcCompanies`, `useCompanyQuestions`, `useLeetCodeSolvedSlugs`, `useJobPostings`) that fetch from Supabase into `useState`.
