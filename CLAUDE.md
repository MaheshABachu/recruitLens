## Supabase

Project `recruitLens` (`sytbbdmrkzfrpqtmioiv`), same org as the sibling `interview-os` project. Tables:
- `profiles` — the app's user table, one row per `auth.users` row (`id uuid primary key references auth.users(id)`, plus `email`), kept in sync by a `handle_new_user()` trigger on `auth.users` insert. A place to hang per-user preferences (e.g. a future email-alert opt-in). `onboarded_at` (null = not yet) drives the onboarding tour — clients can update only that column on their own row (`profiles_update_own` policy plus a column-level `grant update (onboarded_at)`; see `supabase/migrations/20261104120000_profiles_onboarded_at.sql`, which also backfilled accounts that existed before the tour). `handle_new_user()` is `SECURITY DEFINER` and has `EXECUTE` revoked from `anon`/`authenticated`/`public` (see `supabase/migrations/20260828220100_restrict_handle_new_user_execute.sql`) since it's only meant to run via the trigger, not be called directly.
- `leetcode_account` — one row per user (`user_id uuid primary key references auth.users(id)`). Holds `username`, `sync_status` (`'idle' | 'syncing' | 'error'`), `last_synced_at`, `last_error`, and the solved-count stats (`solved_count`/`easy_count`/`medium_count`/`hard_count`).
- `user_companies` — per-user company flags for the Company Questions tab, one row per `(user_id, company_name)` (PK; `user_id` defaults to `auth.uid()`, `company_name` free text matching `lc_companies.name`). Holds `is_pinned`/`pinned_at` (pinned companies lead the quick-pick grid, ordered by `pinned_at`) and `is_in_process` (the header's "In process" toggle — setting it also pins the company, and Pin is disabled while it's on). RLS: authenticated, own rows only. Read/written via `src/lib/userCompanies.ts` → `useUserCompanies` (optimistic, background upserts that only write the flags being changed). Replaced the short-lived `pinned_companies` table.
- `leetcode_problems` (shared/global — LeetCode problem metadata, not user-owned, `slug` unique) / `leetcode_solves` (child, `problem_id` FK `on delete cascade`, `user_id` FK, `unique (user_id, problem_id)` — one solve per problem *per user*, not globally) — populated by the `leetcode-sync` Edge Function from LeetCode's public GraphQL API. That API hard-caps `recentAcSubmissionList` at 20 entries regardless of the requested limit, so a sync only ever sees the most recent 20 accepted submissions — `leetcode_solves` accumulates across repeated syncs, it isn't backfilled in one shot. Besides the manual Sync / Resync control next to the Company Questions heading (`src/components/companies/LeetCodeSync.tsx`), `useLeetCodeSync` fires a silent change probe (`{ mode: "check" }`) on app load and tab refocus, throttled to once per 5 min via `leetcode_account.last_checked_at`: the function fetches only the newest accepted submission and runs the full sync only if its id differs from `latest_submission_id`. `last_changed_at` bumps only when a sync saw new submissions — `useLeetCodeSolvedSlugs` refetches on it. `pg_cron` background resync is still deferred (see `leetcodeSyncTodo.md`).
- `lc_companies` / `lc_questions` / `lc_topics` / `lc_question_topics` / `lc_company_questions` — normalized `[company] -> [time window] -> [question]` schema, sourced from `github.com/liquidslr/leetcode-company-wise-problems` (~470 companies) and imported via `scripts/import-company-questions.ts` (`npm run import:company-questions`, one-off/rerunnable, needs a `SUPABASE_SERVICE_ROLE_KEY` in `.env.local` — never `VITE_`-prefixed, must not reach the client bundle). `lc_questions` is deduped by LeetCode slug; `lc_company_questions` is the fact table (`company_id`, `question_id`, `time_window` one of `'30days' | '3months' | '6months' | '6months_plus' | 'all_time'`, `frequency_score`, `acceptance_rate`), one row per `(company, question, time_window)`. `lc_topics`/`lc_question_topics` hold each question's LeetCode topic tags (e.g. "Array", "Hash Table") as a real many-to-many relation, not a flattened string. Not managed by this app at runtime — imported separately, read-only from the frontend via `src/lib/companyQuestions.ts` (matches `lc_companies.name` by exact, case-insensitive name). Rendered by the `Company Questions` tab (`src/components/companies/CompaniesBoard.tsx`): a quick-pick grid (`FeaturedCompanies.tsx` — a selected company that's neither pinned nor featured takes the first slot, then the user's pins, then a hardcoded featured list filling the rest) plus full-bank search (`CompanyPicker.tsx`). Tiles show live stats from the `company_stats(names text[])` SQL function (distinct questions, how many were asked in the last 30 days, easy/medium/hard mix, and the caller's solved count via `leetcode_solves`), and before a company is picked the board shows `TrendingQuestions.tsx` from `trending_questions(max_rows)` (questions asked by the most companies in the last 30 days). Both are `SECURITY INVOKER` (so RLS keeps `solved` per-user) — see `supabase/migrations/20261030120000_company_stats_functions.sql`, called via `src/lib/companyStats.ts`. **Company hues:** every company gets one of eight `--hue-*` tokens (`tokens.css`, light and dark values) via `src/lib/companyColors.ts` (hand-picked for the featured list, hashed otherwise), shown as a two-letter `CompanyMonogram`; picking a company sets `--company-hue` on `.companies-board`, and the progress arc, radar, topic bars, frequency bars, pin buttons and active filters all derive from it (falling back to `--accent` elsewhere). Schema DDL lives in `supabase/migrations/` (also applied directly via the Supabase MCP `apply_migration` tool — no local Supabase CLI project in this repo).
- `job_postings` — new-grad postings synced every 30 minutes from three GitHub-hosted lists (`jobright-ai/2026-Software-Engineer-New-Grad`'s README table, `speedyapply/2027-SWE-College-Jobs`'s `NEW_GRAD_USA.md` tables, `SimplifyJobs/New-Grad-Positions`'s structured `.github/scripts/listings.json`) via `scripts/import-job-postings.ts` (`npm run import:job-postings`, same service-role-key convention as the LeetCode import). Dedup key is `url_key`, a generated column normalizing the apply `url` (lowercased, query/fragment stripped) — the same posting appearing in 2+ source lists collapses into one row, with `sources` (a `text[]`) recording which lists cited it, rather than "filtering out" the duplicate by dropping it. Rows are soft-deleted (`is_active = false`) when a sync no longer sees them in any source, never hard-deleted, matching the `leetcode_*`/`lc_*` convention. Scheduled every 30 minutes via `.github/workflows/sync-jobs.yml` (this repo's only GitHub Actions workflow — needs `VITE_SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set as repo secrets); also runnable manually. Read in the frontend via `src/lib/jobPostings.ts` → `useJobPostings` → the `Jobs` tab's `JobsBoard` component (rows in `JobRow.tsx`) — browse/filter only. Rows are grouped under sticky date headers when sorted by newest, carry the company's hue/monogram (`src/lib/companyColors.ts`), and filter by category, source, work model and toggle chips (visa blockers, FAANG+, has salary, new this week). A row whose company is in `lc_companies` (case-insensitive) gets a **Prep** chip with its question count (`company_stats`); clicking it calls `onPrepCompany`, which sets App's lifted `selectedCompany` and switches to Company Questions. Data caveats: only SimplifyJobs labels sponsorship/citizenship, and on only a handful of postings, so the visa chip hides known blockers rather than guaranteeing sponsorship; the importer resolves the markdown lists' "↳" (same company as the row above) and only flags `advanced_degree_required` when a posting accepts nothing below a Master's. If any source fails to fetch, that feed skips its soft-delete pass for the run, so a failed fetch can't deactivate postings.
- `company_domains` — company name → website domain for logos (`supabase/migrations/20261104130000_create_company_domains.sql`). Keyed by `name_key` (`lower(trim(name))`, shared by `lc_companies.name` and posting `company` spellings). `domain` null = looked up, no confident match (kept so it isn't re-queried; `--retry-misses` re-queries). `source` is `'manual'` (hand-curated `MANUAL` map in `scripts/import-company-domains.ts`, always upserted, never overwritten) or `'logo_dev'` (Logo.dev brand search, exact normalized-name match only, needs `LOGO_DEV_SECRET_KEY`, capped at 400 lookups/run). Run via `npm run import:company-domains`; also a `continue-on-error` step after each job sync in `sync-jobs.yml`. Select-only for `anon`/`authenticated`. The frontend loads the whole map once (`src/lib/companyLogos.ts`, `useSyncExternalStore`) and `CompanyMonogram` renders `img.logo.dev/<domain>?token=VITE_LOGO_DEV_TOKEN&theme=<light|dark>&fallback=404` on a neutral plate with a company-hue ring, falling back to the two-letter monogram when there's no token, no domain, or the image errors. Logo.dev's free tier requires attribution — the account menu shows "Logos provided by Logo.dev" whenever logos are on; keep it.
- `internship_postings` — same columns and dedup as `job_postings`, filled by the same script and workflow (one `Feed` entry per table) from `jobright-ai/2026-Software-Engineer-Internship`'s README table, `speedyapply/2027-SWE-College-Jobs`'s `README.md` (USA internships) and `SimplifyJobs/Summer2027-Internships`'s `listings.json`. The importer drops Simplify internships whose named terms have all ended (listings with no term or `N/A` stay) and merges Simplify's duplicate category names. Rendered by the `Internships` tab, which is `JobsBoard` with `kind="internships"` (`useJobPostings(kind)` picks the table).

**Auth is real per-user multi-tenancy** (`supabase/migrations/20260828220000_add_user_scoping.sql`). `AuthContext` (`src/context/AuthContext.tsx`, consumed via `useAuth()`) wraps Supabase Auth: Google OAuth plus email/password sign-in, sign-up (email + password only, nothing else collected) and password reset. `App.tsx` renders the marketing `LandingPage` (`src/components/landing/LandingPage.tsx`, styles in `src/styles/landing.css`) until a session exists — its Sign in / Sign up / "Start your free week" buttons open `AuthDialog` (a native `<dialog>` around `src/components/auth/AuthForm.tsx`), and its live counts come from `src/lib/landingStats.ts` (the `landing_stats()` SECURITY DEFINER RPC, which returns only counts). "Confirm email" is off in the project, so email sign-up signs the user straight in (`AuthForm` still handles the "check your email" case if it's ever turned back on). Email sign-up also takes an optional LeetCode username, stored as `user_metadata.leetcode_username`; `useLeetCodeSync` connects it on first load when no account is linked, then clears it. A password-reset link signs the user in with a recovery session; `AuthContext.passwordRecovery` makes `App.tsx` show `SetPasswordScreen` until they save a new password. Supabase's built-in mailer is heavily rate-limited and only meant for testing — production email needs custom SMTP (Authentication → Emails → SMTP settings in the dashboard). The pricing it shows (3-day free trial, then $7/month, $15/3 months or $50/year; 20% to Rooted Immigrant Collective) is backed by Stripe (see **Billing** below); the display plans (`PLANS`), trial length and charity live in constants at the top of `src/lib/billing.ts`. `App.tsx` and reads `session?.user.id` to pass a `userId` into `useLeetCodeSync`. Requires the Google provider to be enabled in the Supabase dashboard (Authentication → Providers → Google, with a Google Cloud OAuth client whose authorized redirect URI is `https://sytbbdmrkzfrpqtmioiv.supabase.co/auth/v1/callback`) — that's a manual dashboard step, not something in this repo. RLS on `leetcode_account`/`leetcode_solves`/`user_companies` is `authenticated`-only, scoped to `auth.uid() = user_id`. `leetcode_problems`, the `lc_*` question-bank tables, `job_postings` and `internship_postings` are shared/global reference data — not user-owned. **The paywall is enforced in the database** (`supabase/migrations/20261105130000_gate_data_on_access.sql`): `job_postings`, `internship_postings` and `lc_company_questions` are readable only by `authenticated` callers for whom `has_app_access()` is true (trialing/active/past_due subscription, or account younger than the 3-day trial — keep its interval in sync with `FREE_TRIAL_DAYS`); `anon` has no select on them. `company_questions()`/`company_stats()`/`trending_questions()` are SECURITY INVOKER so they inherit this. `lc_companies`/`lc_questions`/`lc_topics`/`lc_question_topics`/`company_domains` are public read-only. Clients have no insert/update/delete/truncate on any of these; only the importers write them, with the service role. Note this applies even when `VITE_BILLING_ENABLED` is off: without a subscription, data disappears once an account is 3 days old.

**Edge Function:** `leetcode-sync` (deployed via Supabase, not part of this repo's build — see the project's Edge Functions in the Supabase dashboard) calls LeetCode's public GraphQL endpoint server-side (the browser can't call it directly — LeetCode's CORS headers only allow `leetcode.com` as an origin) and writes to `leetcode_account`/`leetcode_problems`/`leetcode_solves` using the service role key. Invoked from the frontend via `supabase.functions.invoke("leetcode-sync", { body })` in `src/lib/leetcode.ts` — an empty body resyncs the already-connected username, `{ username }` connects a new one. `supabase.functions.invoke` forwards the caller's session JWT automatically; the function decodes it (`supabase.auth.getUser(token)`) to get the caller's `user_id` rather than trusting a client-supplied value, since `verify_jwt: true` already guarantees the gateway rejected unauthenticated calls before the function body runs.

**Billing (Stripe):** three plans — monthly $7, quarterly $15, yearly $50 (20% of revenue goes to Rooted Immigrant Collective — copy only, no Stripe Connect/automatic transfer). The free trial is **in-app, not Stripe**: `FREE_TRIAL_DAYS` (3) from `auth.users.created_at`, no card; `useSubscription(userId, createdAt)` grants access until then and flips to the paywall when it ends (client-side, like the rest of the paywall). Stripe Checkout has no trial. (Subscriptions started before this change may still be `trialing` on Stripe's old 7-day trial; `has_used_trial` is legacy.) Gated by `VITE_BILLING_ENABLED`; when on, signed-in users past the trial without a `trialing`/`active`/`past_due` subscription see `src/components/billing/Paywall.tsx` (a plan picker) instead of the app — during the trial the account menu's "Choose a plan" opens the same screen with a Back button, and the account menu (`src/components/layout/AccountMenu.tsx`, the avatar in the top-right corner) gets a "Manage billing" item linking to the Stripe Billing Portal, with a status line from `subscriptionStatusLine` in `src/lib/billing.ts`.
- `subscriptions` table (`supabase/migrations/20261029180000_create_subscriptions.sql`) — one row per user mirroring their Stripe customer/subscription. RLS: authenticated can `select` own row only; writes come only from the Edge Functions via service role. Read via `src/lib/billing.ts` → `useSubscription` (polls after `?checkout=success` until the webhook lands).
- Edge Functions (source in `supabase/functions/`, shared helpers in `_shared/billing.ts`): `stripe-checkout` (`verify_jwt: true`; allows Stripe promotion codes; `{ action: "checkout" | "portal", plan?: "monthly" | "quarterly" | "yearly" }` → returns a Stripe URL; plan → lookup key via `PLANS` in `_shared/billing.ts`) and `stripe-webhook` (**must** be deployed with `--no-verify-jwt`; verifies `Stripe-Signature`, re-fetches the subscription from Stripe and upserts the row). Both need Supabase secrets `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`; without them they return a 503 "Billing isn't set up yet".
- `npm run setup:stripe` (`scripts/setup-stripe.ts`, idempotent) creates the product + one price per plan (lookup keys `vantage_monthly` / `vantage_quarterly` / `vantage_yearly` — checkout falls back to an inline price if one is missing; changing a plan's cents/interval and re-running creates a new price, moves the lookup key to it and archives the old one, so existing subscribers keep their old price), the webhook endpoint at `<VITE_SUPABASE_URL>/functions/v1/stripe-webhook`, and a Billing Portal configuration (re-running updates it; includes prorated switching between the three plans), then prints the `supabase secrets set` command.
- Going live: `STRIPE_SECRET_KEY` in `.env.local` → `npm run setup:stripe` → set the two Supabase secrets → apply the migration → `npx supabase functions deploy stripe-checkout --project-ref sytbbdmrkzfrpqtmioiv` and `npx supabase functions deploy stripe-webhook --no-verify-jwt --project-ref sytbbdmrkzfrpqtmioiv` → `VITE_BILLING_ENABLED=true`. Test-mode keys (`sk_test_…`) first; re-run the whole list with `sk_live_…` for production (live mode has its own price/webhook/secret).
- Type-check the functions with `cd supabase/functions && npx deno check --node-modules-dir=none stripe-checkout/index.ts stripe-webhook/index.ts` (without that flag Deno trips over the repo's `node_modules`).

## Architecture

React 18 + TypeScript + Vite. Styling is hand-written CSS custom properties (`src/styles/tokens.css` + `global.css`, plus `landing.css` for the signed-out landing page) — no Tailwind, no CSS framework. No React Router — the tab bar is local state in `App.tsx`. No global state library.

`App.tsx`'s `Tab` union is `"Company Questions" | "Jobs" | "Internships"`, all functional. If a new tab is added to the union before it has a real view behind it, render it disabled with a "Soon" badge (`tab-bar__tab--disabled` / `tab-bar__soon`), don't build a placeholder page for it.

**Onboarding tour:** `src/components/onboarding/OnboardingTour.tsx` runs a `driver.js` spotlight tour (styled with tokens in `src/styles/tour.css`) the first time an account reaches the app — after the paywall when billing is on. `useOnboarding` reads/writes `profiles.onboarded_at` via `src/lib/onboarding.ts` (plus a `vantage-onboarded:<userId>` localStorage flag so a failed save doesn't re-show it). Finishing, skipping or closing all count as done; the account menu's "Take the tour" replays it, after switching back to Company Questions with no company selected. Steps target `data-tour="…"` attributes (`picker`, `featured`, `leetcode`, `trending`, `tabs`, then on the Internships tab `job-toggles`, `job-row`, `prep`, then `account`) — keep them when refactoring `App.tsx`, `CompaniesBoard`, `FeaturedCompanies`, `LeetCodeSync`, `TrendingQuestions`, `JobsBoard`, `JobRow` or `AccountMenu`. Next on the `tabs` step switches App to Internships (via the `onShowTab` prop) and waits for postings to load; Back on it returns to Company Questions. Elements are looked up when each step is shown (boards remount on tab switch); a missing Company Questions element drops its step at start, a missing Internships one falls back to the first row / tab bar.

**State:** `AuthContext` for the login gate, `ThemeContext` (`src/context/ThemeContext.tsx`, light/dark, persisted to `localStorage` under `vantage-theme`; switched from the account menu in the app, and from `ThemeToggle` on the signed-out/paywall screens), and otherwise plain per-feature hooks (`useLeetCodeSync`, `useUserCompanies`, `useLcCompanies`, `useCompanyQuestions`, `useLeetCodeSolvedSlugs`, `useJobPostings`) that fetch from Supabase into `useState`.

**Caching / load performance:** `src/lib/swrCache.ts` is a stale-while-revalidate cache (memory + IndexedDB `vantage-cache`, `useSwr`/`prefetch`) for global reference data only — never user-scoped data. `useJobPostings` (5 min max age; pages fetched in parallel after a counted first page) and `useCompanyQuestions` (24 h; one `company_questions(company_name)` RPC returning a jsonb array, see `supabase/migrations/20261105120000_company_questions_function.sql`) use it, so revisits render instantly and refresh in the background. Bump `CACHE_VERSION` when a cached shape changes. `App.tsx` lazy-loads every screen/board (`React.lazy`), the onboarding tour (driver.js) and `RadarChart` (recharts) are separate chunks, and once idle App preloads the other boards' code and both posting lists. `vite.config.ts` splits `react` and `supabase` vendor chunks; `vercel.json` serves `/assets/*` as immutable.

**Legal pages:** `/terms` and `/privacy` (`src/components/legal/LegalPage.tsx`) render from `main.tsx` before `App` (no router; `vercel.json` rewrites both paths to `index.html`), so they work signed in or out. Operator, contact email, governing law and last-updated date are in `src/lib/legal.ts`; plan prices, trial length and charity come from `src/lib/billing.ts`. Linked from the landing footer, sign-up form, paywall and account menu. Drafts, not legal advice.

**Account deletion:** account menu → Delete account → `src/lib/account.ts` → `delete-account` Edge Function (`verify_jwt: true`), which cancels any live Stripe subscription immediately and then deletes the auth user (all user tables cascade). `stripe-webhook` treats a foreign-key violation (user gone) as handled so Stripe doesn't retry.

**Monitoring:** `src/lib/monitoring.ts` injects Vercel Web Analytics + Speed Insights in production builds (both enabled in the Vercel dashboard). No error monitoring. Favicon, apple-touch icon and the Open Graph image live in `public/`.

**Job sync cadence:** GitHub's `schedule` trigger fires every 4-8 hours in practice. `supabase/migrations/20261105140000_dispatch_job_sync_cron.sql` adds a `pg_cron` job that calls the workflow's `workflow_dispatch` API every 30 minutes, using a GitHub fine-grained token (Actions: read and write) stored in Vault as `github_sync_dispatch_token`; it does nothing until that secret exists.
